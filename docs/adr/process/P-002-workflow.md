# P-002 工作流程

## 當前情境

- 一個人加 AI agent，沒有期限；我排順序、看進度、做決定。
- 流程要輕；只有 one-way door 與規則變化的改動要我看、我合併。

## 決策

**工作項目、里程碑、進度與狀態都在專案管理工具（D-004）裡管，不在這個 repo 的文件裡。** 要動工不必先 commit 一份文件。

| 項目 | 怎麼做 |
|---|---|
| 工作項目 | 一張 GitHub issue，三節：要什麼、驗收條件、種類；大小約一張 PR |
| 誰開與關 | 我和 agent 都能開；agent 開的在對話裡說一聲；PR 合併時用 `Closes #n` 自動關 |
| 狀態 | 開著、關掉兩種 |
| 標籤 | 改動類型一個、種類一個；由 `lawfulv2:labels` 建 |
| 里程碑 | M1 對話迴圈 → M2 規則生成 → M3 場景地圖 → M4 分層慣例；常駐「待排」「發行前」 |
| 分支 | `<前綴>/<issue 號>-<短名>`，例如 `feat/12-render-png`；前綴對應改動類型：feature `feat/`、bug `fix/`、refactor `refactor/`、docs `docs/`、test `test/`、chore `chore/` |
| 審查 | agent 自審（`/code-review`），每張 PR 最多 2 輪 |
| 合併 | 一律 squash merge；誰合見下表 |
| 進度 | 在 GitHub 的 milestone 頁面看 |
| 報告 | 必要的「此次任務的達成目標」「沒做的事」，加上：成果預覽圖、等我決定或合併的事、agent 合併了哪些 PR、派了哪些 agent 與模型 |

**里程碑做完是什麼樣子：**

| 里程碑 | 做完 |
|---|---|
| M1 對話迴圈 | 透過 MCP 建空場景地圖與一個 level，在 IntGrid 畫格、擺 Entity，每步回傳 PNG；LDtk 1.5.3 打得開 |
| M2 規則生成 | 一份規則檔（含 seed）一個指令生成整個 level 的版面；同規則同 seed 結果相同 |
| M3 場景地圖 | 多個 level 加世界佈局，傳送點跨 level 連接，兩種存法都支援，加世界總覽 PNG |
| M4 分層慣例 | 慣例寫成文件與檢查，我的遊戲照慣例讀得進一份生成的村莊 |

**誰合併：**

| 改動 | 誰合 |
|---|---|
| ① `CLAUDE.md`、`docs/adr/**` | 我；PR 標題加 `[需人工合併]` |
| ② 分層慣例（IntGrid 層與 Entity 的命名和意義） | 我；同上 |
| ③ 場景地圖存檔結構（規則檔格式、檔案擺法） | 我；同上 |
| ⑤ 新增或升級主要依賴（例如 `mcp`、Pillow 的大版本） | 我；同上 |
| ⑥ CI、pre-commit、檢查腳本 | 我；同上 |
| 其餘 | agent，條件是 CI 全綠、沒有本次引入的未修發現、PR 附驗證證據（例如 render 出的 PNG） |

**種類的待遇：**每個工作項目標一個種類（判準見 `CLAUDE.md`「工作的種類」）。

| 種類 | 做不做 | 優先序 | 什麼時候做 |
|---|---|---|---|
| 目的 | 做 | 1 | 照里程碑順序 |
| 延伸 | 不做；開 issue 放「待排」 | - | 我點名才做 |
| 工程保證 | 做 | 2 | 會壞場景地圖的掛「發行前」，碰到就修 |
| 效能 | 不做；開 issue 放「待排」 | - | 我點名才做；PNG 慢到影響對話時升級 |
| 開發工具 | 只做擋到開發的（例如 CI、測試夾具） | 3 | 擋到時 |
| 維護 | 擋合併的當場修；其餘放「待排」 | - | 擋到時 |

**第二把尺：**架構規範：P-003。M4 之後加上分層慣例（見 `docs/adr/README.md`「待決定」）。

`docs/backlog.md` 只記還開不成工作項目的點子；定下來就搬進專案管理工具，並從 backlog 刪掉。

## 三個月後的影響

- agent 能自己合大部分的 PR，進度快；漏審的風險靠 CI 與自審擋。
- 「要我合併」只靠紀律；agent 判錯類別時，我要事後從報告的「合併了哪些 PR」抓出來。
