# D-014 entity 與傳送點可以指定位置與大小，慣例 entity 可以改外觀，存法可以由規則檔指定

## 當前情境

- WeftEngine 的 rewind-and-reap 要把現有 14 關照原樣改由規則檔產生（utomore/WeftEngine#984）；遊戲讀到的 `px`、大小、顏色、tags 與存法都要跟現在一致（#71）。
- 現在的規則檔寫不出：
  - 同一個類型的房子有 4×3、3×3、6×3 三種大小。
  - 出生點在 (432, 360)，一格 96 像素，不在格子的左上角。
  - 固定位置與大小的傳送點，例如 1×3、3×1。
  - `Teleport` 的顏色 `#30e1b9` 與 tag `tele`。
  - 一律存單檔：遊戲的測試要求關卡都在主檔裡，有人刪掉主檔再生成也不能變成拆開存。
- 情境：Home 的 (4, 3) 那一格往右 48、往下 72 放出生點；Farm 西邊牆缺口放一個 1×3 的傳送點。

## 選擇

| 選項 | 適合 | 代價 |
|---|---|---|
| 逐個實例指定：`[[entity]]` 的 `size`、`offset`；`[[portal]]` 的端點寫固定位置與大小；慣例 entity 覆寫顏色與 tags；規則檔指定存法（選中） | 規則檔照遊戲現在的擺法寫；改一個東西就改它那一行 | 規則檔多幾個欄位；實例大小跟定義不同，定義要設成可縮放 |
| 每種大小宣告一個類型 | 工具不用改 | 遊戲靠類型名稱找東西（例如 `House`），不能拆成三個；每個固定位置的傳送點也要另一個類型 |
| `at` 改寫像素 | 位置與位移一個欄位寫完 | 推翻 D-007 以格與錨點寫位置；錨點算出來的格不能再加位移 |
| 開放 `[[entity]]` 擺 `Teleport` | 傳送點跟別的 entity 一樣寫 | 推翻 D-010 傳送點一律成對互指；成對要另外查，比 `[[portal]]` 容易寫錯 |
| 存法照磁碟（維持 D-002） | 不用改 | 主檔被刪掉再生成就變成拆開存，遊戲的測試讀不到 |

## 決策

- `[[entity]]` 多兩個選填欄位：
  - `size = [寬, 高]`（格，各至少 1）：這個實例的大小，沒寫是類型定義的大小。
  - `offset = [x, y]`（像素，各在 0 到 grid - 1）：實例擺在那一格左上角往右下位移後的位置；`px` 是那一格的左上角加 `offset`（生成的定義 pivot 是 (0, 0)），位移小於一格，所以實例還在那一格。
  - 比一格小的實例（例如 8×8 像素的出生點）：`size` 最小是一格，要宣告 `[entity_types]` 的類型寫像素大小，再用 `offset` 擺。
- 實體的整個矩形（`px` 加上實例的大小）都要在 level 內，不只左上角：
  - 實例的大小是 `size` 乘以格子大小，沒寫是類型定義的大小（範本三種是一格，宣告的類型照 `[entity_types]` 的像素）。
  - 擺在固定格的，讀規則檔就查；擺在錨點的，錨點的格要排了才知道，配置時查。
  - 兩個 entity 擺在同一格的檢查，還是只看左上角那一格；矩形大不算撞到（可耕地上可以擺雜物）。
- `[[portal]]` 的 `from`、`to` 除了錨點，也可以寫固定端點：`{ level = "Farm", at = [38, 4], size = [1, 3] }`。
  - `at` 是左上角的格，`size` 是格、沒寫是 [1, 1]；只有一個 level 時 `level` 可以不寫。
  - 兩端的 `Teleport` 照這個位置與大小擺，`px` 是 `at` 乘以格子大小，沒有 `offset`；iid 與互指照 D-010。
  - 端點的每一格都不能跟同一個 level 別的 entity（左上角那一格）、區域零件、別的端點的格撞到，撞到就報錯。
  - 端點可以蓋在區域或路徑的格上：門本來就開在牆或地板上，端點只管 entity 的格，不碰地形層。
- 有實例的大小跟定義不同的 entity 定義，生成時把 `resizableX`、`resizableY` 設成真，其餘的定義維持範本的值；沒用到的規則檔，定義跟以前一樣。
- `[entity_types]` 可以用分層慣例 entity 的名字（`PlayerSpawn`、`Teleport`、`Part`，分大小寫）覆寫外觀：
  - 只能寫 `color`、`tags`，至少寫一個；寫別的（例如 `size`、`fields`）報錯，名稱、大小與欄位定義不變。
  - `tags` 是整個取代，不是加上去；`PlayerSpawn` 的 tags 一定要有 `player`（D-011），拿掉就報錯，生成的場景地圖才一定照慣例。
  - 沒寫的維持範本的值。
- 規則檔頂層可以寫 `split = true` 或 `split = false`：生成之後的存法就是它，不看磁碟上原本怎麼存、主檔在不在；沒寫就沿用磁碟上的（D-002）。
  - 主檔不在、子資料夾裡還有別人的 `.ldtkl` 時，照舊不覆蓋（那些檔不是生成的）。
  - 存法改變的途中失敗，被刪的與新寫的 `.ldtkl` 都還原，磁碟上的檔不變。
- 生成紀錄把 `size`、`offset` 與固定端點的大小算進元素的位置：改了，摘要列在「位置或欄位變了」。

## 三個月後的影響

- 單位有兩種：`[[entity]]` 的 `size` 是格，`[entity_types]` 的 `size` 是像素（類型的預設大小）；寫錯單位看預覽圖就看得出來。
- 擺在錨點的 entity，矩形出界要到生成才報，讀規則檔時查不到。
- 實體矩形一律要在 level 內：以前宣告的類型比一格大、擺在 level 邊上的規則檔，現在讀或生成時報錯。
- 在 LDtk 裡把 entity 挪幾個像素或拉大，算直接改過（生成紀錄本來就記每個 entity 的像素位置與大小），重新生成要先 force（D-008）；要保留，就寫進 `offset` 或 `size`。
- LDtk 1.5.3 對「定義不可縮放、實例大小不同」怎麼處理，還沒實測；把定義設成可縮放是為了不靠那個行為，打開檔看實例大小有沒有被改回去，寫在 PR 的手動驗收裡。
- 要在傳送點端點上加 `offset`、或讓 `[[entity]]` 的碰撞看整個矩形，再加寫法；不推翻這份。
- 這份改了 D-002（存法）、D-007（`[[entity]]` 的欄位）、D-010（傳送點的端點、`[entity_types]` 與慣例 entity）、D-011（慣例 entity 的外觀可以覆寫），那幾份各加一句指到這裡。
